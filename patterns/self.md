# 本服务自身行为坑（跨应用通用，与具体软件无关）

## wait_for 必须带窗口定位；不带定位扫全桌面必然超时

_记录日期: 2026-09-19 · 状态: **已修复并实测上线**（build 09-19 03:59, commit `c88818b`）_

**踩到的坑**：`/wait_for` 只传 `text` 不传 `hwnd`/`title` 时 `pid=0`，会遍历桌面上**全部**顶层窗口，撞上 Electron 大 DOM 必然 7 秒超时，还白记一个泄漏线程（`leaked_total` 当场从 0 变 1）。

**给调用方**：`wait_for` 必须带 `hwnd=`（`list_apps` 现取）或 `title=`。不带定位现在 **14 毫秒**就被拒（旧版 7 秒超时 + 白烧线程）。“等任意窗口出现某文字”不支持，也不该支持。

**修复内容**：扫描跳过 UIA 禁用应用的窗口（否则 `wait_for` 会绕开入口拦截白烧 8 秒）+ 每窗口限量 250 元素、单窗耗时上限 1200ms，成本有界；`WaitFor` 入口强制定位，并区分“没传定位”和“传了但句柄已失效”两种提示。

**实测数据（全部通过，别只看一条就下结论）**：
- 正向真命中：资源管理器 `text=回收站` → `satisfied:true` `matched:"回收站"`，**84ms / 1 次采样**（服务端精确名过滤走快路径）。
- 反面对照：同窗口等一个真没有的词 → `satisfied:false` 1625ms / **4 次采样**，证明是真在轮询而非扫一次就定论。
- `disappear=1`：不存在即达成，226ms / 1 次。
- 测完 `/health` 的 `uia.leakedTotal` 仍是 0，没再白烧线程。

**方法论教训（值得所有 agent 记）**：`disappear=1` 返回“达成”**不能**当作“扫描读得到内容”的证据 —— 完全读不到时它同样通过。验证探测类能力必须**正负两条各测一次**，我这次差点就被自己的成功案例骗过去。

**同轮已生效的收益**：`expect` 从“睡 900ms 扫一次”改成轮询；配合 `window_state`（零副作用查状态）和按进程隔离的熔断，WorkBuddy 这类必挂应用从“白等 8 秒 + 全服务连坐只能重启”变成 **13 毫秒**拦下并给出替代路子。
