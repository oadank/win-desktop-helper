## D8 — WorkBuddy 主窗口：UIA 会超时，导航只能靠坐标；误点会切走整个分区（2026-09-18 实测）

**UIA 不可用**：`ui_tree` / `ui_find` / `ui_click` 对 WorkBuddy 主窗口（Electron 大 DOM）**全部 8s 超时**（`UIA timeout 8000ms - 疑似大DOM`）。→ 老实走截图 + 坐标，别反复试 UIA 浪费轮次。

🔴 **连 `ui_find(name=...)` 也会把整个服务熔断**（2026-09-18 08:09 实测）：在 WorkBuddy 上跑一次 `ui_find(hwnd=..., name="描述任务")` 就返回 `UIA fused: 3 leaked worker threads (大DOM 超时不可杀)`，**此后所有 `/ui/*` 一律拒绝**（不是单窗口失效，是全服务级熔断；泄漏线程杀不掉，只能重启）。
修复：`taskkill /F /IM shot-service.exe` → `schtasks /run /tn WinDesktopHelper` → `curl 127.0.0.1:18800/health` 看到新 pid + `elevated:true` 即恢复（实测 5 秒内起来）。
**结论：WorkBuddy 主窗口上任何 `/ui/*` 都不要调，一次都别试。**

补充实测（2026-09-18 08:1x）：MiMo 客户端**可以**用 `ui_find(type="Edit")` 拿输入框精确 rect（见 D7），但那是熔断之前的事；熔断当场就再也用不了。所以给 Electron 客户端贴长文时，**优先一次就用 ui_find 拿准 rect，别先试错**。

## WorkBuddy 自带网页调试通道（9223），可 1ms 读出整张可点元素表 —— 桌面自动化不必 OCR

_记录日期: 2026-09-26 · 应用: WorkBuddy_

2026-09-26 老大批准"只读探测"后当场实测（纯读，未点任何按钮）：

■ 事实
- WorkBuddy 主进程启动参数里**自带** `--remote-debugging-port=9223`（Electron 37.10.3 / Chrome 138，公司 Tencent）。
- `GET http://127.0.0.1:9223/json` → 1 个 page target（app.asar 里的渲染页）；拿它的 webSocketDebuggerUrl 连上，发一条 `Runtime.evaluate`：
  用 `button,[role=button],[role=menuitem],a[href],input,textarea,[class*=btn]` 过滤可见元素，
  **页面内 JS 耗时 1ms，一次拿到 81 个可点元素**，每条含 标签/role/可见名字/x,y/宽。
  样本：`BUTTON/tab「新建任务」@12,92 宽240`、`BUTTON/tab「定时任务」@12,220`、`DIV/button「agents-to-feishu 15天前」@12,359`。
- 对比：buddy_checkin 领积分一次 claimed 全程 **17 次串行本地 VLM OCR ≈ 112 秒**（见 openmem `0cf11a3b`）。
  **同一件事换成读元素表 = 1 毫秒级、零截图、零认字。**

■ 结论（纠正两条旧账）
1. 手册铁律 8 说 workbuddy 在 UIA 入口直接拦 —— 那是**走系统无障碍**这一条路的结论。WorkBuddy 有**更好的第三条路：CDP 直读 DOM**，与本机 `patterns/edge-cdp.md`（划词悬浮球 CDP 直读链）同一族，别只记"UIA 不通就退回截图+坐标"。
2. 桌面自动化提速的正确顺序：**① CDP 读元素表（能读到就根本不 OCR）→ ② 读不到（原生菜单/系统弹窗）才截图+OCR → ③ 决策模型只负责在元素表里做 N 选 1**（点哪个/是不是已领取/要不要重试）。

■ 探测姿势与坑（实测踩到）
- 托盘唤回 `app(action=tray,name=WorkBuddy)` 本次返回 `via=relaunch`（**把应用重启了**，不是置前）→ 之前用 `window(list)` 采到的 hwnd 立刻变死句柄。
  我拿旧句柄 328806 去问 UIA，得到 `IsWindow=False` + `FromHandle=null`，**差点据此下"UIA 完全看不到这扇窗"的错误结论**。
  纪律：**唤窗/重启后必须重新采句柄**；`FromHandle` 返回 null 先怀疑句柄死了，不是应用不给树。
- 用 `AutomationElement.RootElement.FindAll(Children, ProcessId=某PID)` 数 WorkBuddy 窗口会得 0 —— Electron 的窗口常挂在**别的子进程**上（`Get-Process.WorkBuddy.MainWindowHandle` 也可能全 0）。按 pid 过滤找不到 ≠ 窗口不存在，用 `window(list, process=WorkBuddy)` 拿真句柄。
- CDP 是**能改界面**的通道（可发任意 JS）。默认只用 `Runtime.evaluate` 读；任何 click/输入都算敏感操作，先问老大。

■ 🔴 2026-09-26 修掉桥侧两个 bug（改的是 `mcp-bridge.js` 里 `cdp` 工具的**实现**，不只改文档）

1. **`selector` 读不到影子根里的元素**（`elements selector=.fuel-close` 回 0 条，元素明明在）：原 walk 是「先在本层 `querySelectorAll(sel)`，**命中了才**递归它的 shadowRoot」——影子根内的元素，host 本身不匹配 selector，于是**永远进不去**。改法：把 host 递归移到匹配循环**之外**、**无条件**执行
   `for (const h of root.querySelectorAll('*')) if (h.shadowRoot) walk(h.shadowRoot, d + 1);`
   ⚠️ 这个 bug 与主手册纪律 2「必须用 selector 收窄」正面冲突——照纪律做必然 0 条；`match=` 那条路（全量 + 文本过滤）恰好正常，所以一直没暴露。
2. **靠 `aria-label` 命名的图标按钮被整体丢弃**：`own`（自有文本节点拼出来）是**一个空格**，在 JS 里 **truthy** → 把 `|| aria-label` 全短路掉，`.trim()` 后成空串 → 元素被跳过。`.fuel-close`（× 按钮，文字在 SVG 里、只有 `aria-label`）就是这样**从来读不到**。修法：`join(' ').trim()`。
   ⇒ 泛训：**「纯空白字符串」在 `||` 链里是 truthy** —— 任何 `a || b` 兜底，先把 `a` `.trim()` 再判。

**改这段 expr 必跑的三条自检**（光看语法通过不算数，本轮就是这么被骗过一轮的）：

- **a. 括号配平 + `new Function(expr)`** —— 语法检查；
- **b. 作用域结构断言** —— `for (const e of ...)` 必须在 `for (const h of ...)` **之前**闭合；否则 host 递归被套进匹配循环，退化成"有匹配才进影子根"（语法完全合法，只有断言能发现）；
- **c. 端到端实跑** —— `selector=.fuel-close`（影子根内）应 ≥1 条、`selector=.user-menu-trigger`（顶层）应 1 条、`click` 后回读 `.fuel-btn` 应归 0。

■ 🔴 2026-09-26 定案：**领积分不再贴边** —— 通道定位与窗口位置无关，但**探区必须跟随 `rect`**

贴左（`/win/snap?pos=left`）过去唯一的作用是**让截图像素坐标可预测**（OCR 要在固定框里认字）。
定位改走通道（读 DOM）后这个前提消失 → 默认不贴边：省 ~2s，且不再把用户摆好的窗口挪走。
**代价**：所有「屏幕绝对坐标探区」立刻失效。去贴边时必须一并改成**跟随窗口 rect**（本仓踩到的 2 处）：

| 旧写法（屏幕绝对，只在贴左时对） | 新写法（跟随 rect） | 位置 |
|---|---|---|
| `PANEL_PROBE = (0, 950, 480, 490)` | `panel_probe(rect)`：`py = rect.y + rect.h - PANEL_H` | `scripts/buddy_checkin.py` |
| `SIDEBAR_TOGGLE_PROBE = (0, 0, 150, 90)` | `(rect.x, rect.y, 150, 90)` | 同上（侧栏收起时才走到） |

⇒ 泛训：**凡探区常量，先问一句「窗口不贴左时它还框得住吗」**；框不住的写成 `rect.x/y + 偏移`。
（相对头像/菜单的探区本来就用 `rect` 算，天然没这个问题 —— 只有"屏幕角落"型探区会中招。）

■ 实测（窗口放在右半屏 x=1280，非零原点，`dpr=1.25`）
- 通道算头像圆心 (1323,1338) vs 像素法扫绿圆 (1324,1337.5) → **差 1px，两法一致** ✓（证明 `屏幕 = 窗口原点 + 页面×dpr` 在非零原点下依然成立）
- `--dry` 全流程 **2.1s**、每步 `via=cdp`、`window_placed=keep`（一步没动窗口）
- ⚠️ `rect_ok=false` 是**正常现象**（该日志只在贴边态才为 True），别据此判故障
- 兜底口径：窗口宽/高 <400 或与屏幕几乎无交集 → `rect_usable()` 判否 → 自动贴一次左再跑

## 删除侧栏聊天记录（会话项）—— 右键「删除任务」全链路

_记录日期: 2026-09-26 · 应用: WorkBuddy · 实测：**脚本化删除 6 条同名会话，全部成功（`ok:true`）**_

**结论：右键前先确认没有抽屉遮罩层残留（`_drawerBackdropOpen`），然后右键 → 删除任务 → 确认。**

已固化为脚本：`C:\D\opt\scripts\wb_delete_conversations.py`（`--list / --match / --id / --older-than / --yes`，默认 dry-run）。

### 🔴🔴 坑 0（最狠，2026-09-26 花一整轮才定位）：抽屉遮罩层吃点击

**症状**：`/mouse/click?button=right` **返回 `ok:true`**，但界面**毫无反应**，右键菜单不弹。
这是最难查的一类"假成功"——工具说点成功了，界面说什么都没发生。

**根因**：WorkBuddy 侧栏抽屉遗留了**遮罩层**。
```
_drawerBackdrop_7xbcw_157 _drawerBackdropOpen_7xbcw_170   ← z-index 200，1024×1074，pointer-events:auto
父容器 _grid_7xbcw_4 额外带类 cb-grid--drawer-open
```
遮罩铺在侧栏上方，**吃掉所有点击**（左键/右键都吃）。
这是**自己操作留下的状态**（抽屉开过没关干净），不是常驻现象。

**🔴 判定口诀（最重要的一条泛训）**：
> 事件**到了页面但 target 不对**（= backdrop/overlay）→ **有层盖着**，去清遮罩。
> 事件**根本没到页面** → 才去查钩子 / 权限 / UIPI。

**查法**（CDP 挂监听，一眼看穿）：
```js
document.addEventListener('contextmenu', e => window.__t = e.target.className, true)
// 右键后读 window.__t
// → 正常应拿到会话项 class；若拿到 `_drawerBackdrop_...` 就是遮罩在吃事件
```

**修法**（两条都要，缺一残留）：
```js
document.querySelectorAll('[class*=drawerBackdrop]').forEach(e => e.remove());
document.querySelector('[class*=cb-grid--drawer-open]')?.classList.remove('cb-grid--drawer-open');
```
⚠️ Esc 和"点遮罩空白"**都关不掉**（实测），必须直接 remove。

**❌ 已被证伪的旧结论（别再信，别照做）**：曾误判为「win-desktop-helper 划词取词钩子吞右键」，
并据此写了"必须先 `GET /pick-config?enabled=0`"。**这个结论是错的**：

| 对照实验（2026-09-26 重做） | 右键菜单项数 |
|---|---|
| 取词 OFF ×3（遮罩开着） | **0** |
| 取词 ON ×3（遮罩开着） | **0** |
| 取词 ON（**清掉遮罩**） | **5** ✅ `['批量操作','打开文件夹','重命名','分享任务','删除任务']` |

⇒ **取词与右键能否弹出完全无关**。代码层也自证：`PickOnMouse()` 返回 `void`，
回调里只有两处 `return (IntPtr)1`，且**只针对任务栏**（中键静音 / 滚轮音量）；
`LowLevelHooksTimeout` 实测 **1000ms**（旧注释写的"1ms"是过时注释）。
**⇒ 别再关取词**，它是老大的日常划词翻译功能，从来不是原因。

**泛训**：`/mouse/click` 返 `ok:true` **只代表"鼠标事件发出去了"**，不代表目标元素收到事件。
工具报成功但界面无反应时，**先用上面的口诀分流**（到了页面 → 查遮罩；没到 → 查钩子）。
本机确实存在低级鼠标钩子（`shot-service.cs` 的 `WH_MOUSE_LL`），但那不是本例元凶。

### 🔴 坑 1：别在全屏按文字搜「确认」——聊天正文里就有

全量元素表（`elements(limit=600)`）**包含聊天记录正文**。实测搜「确认」命中了
屏幕 `y=-9141` 的历史消息（我自己的分析稿），点到视口外 → 无效。
